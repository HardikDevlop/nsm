# SNMP Interface Timezone Runtime Fix

The proven crash was the expression `(now - prev["created_at"]).total_seconds()` in `_persist_interfaces()`. `now` is generated by the application through the canonical `utc_now()` helper and is offset-aware UTC. `prev["created_at"]` is loaded from the legacy `InterfaceStatistic.created_at` DateTime column and can be offset-naive while semantically representing UTC. Python rejects subtraction of those mixed datetime types.

The persistence path now uses the existing `as_utc(..., legacy="UTC_NAIVE")` helper for both operands before subtraction. No IST conversion, tzinfo stripping, fabricated timestamp, database update, collector change, counter change, rate formula change, or transaction change was introduced. Missing previous timestamps retain the existing 60-second fallback; zero and negative elapsed values remain excluded by the existing `elapsed > 0` guard.

Files changed:

- `hardik/backend/services/snmp_polling.py`
- `hardik/tests/test_snmp_interface_timezone_fix.py`

Focused tests cover naive DB UTC plus aware application UTC, aware/aware arithmetic, numeric elapsed values, missing/zero/negative protection, and absence of manual IST conversion. Python compile validation was run. Full pytest/runtime verification is environment-dependent; localhost/device runtime verification was not attempted.

The immediate `_persist_interfaces()` path contains no other datetime subtraction or comparison. Its only datetime arithmetic is now normalized through the canonical helper.
